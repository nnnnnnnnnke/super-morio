# スーパモリオ — Super Morio

**ネットワーク遅延を「体で」学ぶための、サーバ権威型2Dアクションゲーム。**

キャラクターの位置も、敵の動きも、コウラの跳ね返りも、すべて**サーバ**が計算します。
ブラウザは「キー入力を送る」「返ってきた状態を描く」だけ。
だから **経路が遅いと、操作そのものが遅れます** — 遅延500msの経路では、0.5秒前に着地点を決めてジャンプするしかありません。

もともとはインターネット体験会の演習教材として作ったものです。ルータの経路を
切り替えて「高遅延の道」「細い道」「快適な道」を通し、同じゲームの操作感が
どう変わるかを体感してもらう、という使い方をしました。

## しくみ

```
ブラウザ (描画のみ)                     サーバ (Raspberry Pi / PC)
┌───────────────┐   キー入力 (60Hz)   ┌──────────────────────┐
│ canvas 描画    │ ──── WebSocket ──→ │ 60Hz 固定ステップで    │
│ 補間・演出・音  │ ←── 状態 30Hz ──── │ 世界を進め続ける常駐ループ│
└───────────────┘  (フォールバック:    └──────────────────────┘
                    HTTP ポーリング)
```

- **サーバ権威 + 常駐60Hzループ**: 世界は実時間で進み続ける。ネットワークが遅れて
  影響するのは「入力が届く時刻」と「絵が見える時刻」だけ
- **WebSocket優先・HTTPフォールバック**: 切断時は自動でポーリングに退避し、5秒ごとに復帰を試みる
- **クライアント補間**: 30Hzの状態を指数追従で60fpsに変換(現代ネトゲの基本)
- 依存は Flask / gevent / simple-websocket のみ(Debianなら全部aptで入る)。
  音楽・効果音はWeb Audioでリアルタイム合成(2A03流)、絵はcanvasで手描き — **外部アセットゼロ**

## ゲーム内容

- 3ステージ: ちじょう / どうくつ / コッパじょう(ボス戦: 炎とファイアバーをかわして斧で吊り橋を落とす)
- SMB1系の物理を「高さと時間」から逆算して実装: 慣性・スキッド・可変ジャンプ・二段ジャンプ・
  コヨーテタイム・ジャンプバッファ・コーナー補正・頂点の重力減衰
- 仕掛け: ?ブロック / 絵柄が回るルーレットブロック / キノコ(1回だけ被弾を肩代わり) / スター無敵 /
  ばね / 氷床 / ベルトコンベア / 崩れる床 / はねガメ / ずどん砲台 / 上下リフト / きのこへい大行列
- 踏みつけチェーン(×コンボ表示)・コウラ蹴りの連鎖・旗の掴み高さボーナス・S/A/B/Cランク評価と自己ベスト

### 遅延教材としての仕掛け

| 仕掛け | 教えてくれること |
|---|---|
| ルーレットブロック (0.66秒/コマ) | 遅延0.5秒の経路では「今見えている絵柄」は過去。先読みして叩くしかない |
| ファイアバー (決定論で回転) | 周期が読めるものは、遅延があっても**予測**で勝てる |
| きのこへい大行列 (踏みチェーン) | サーバ内で完結する処理は遅延の影響を受けない |
| 崩れる床 | 「乗ったのが見えた」時点で、崩壊タイマーはとっくに燃えている |

## 動かし方

### ローカルでさっと遊ぶ

```bash
uv run --with flask --with gevent --with simple-websocket tools/run_local.py
# → http://localhost:5099/morio
```

`?embed=1` を付けると、キャンバスと HUD だけを表示します (投影用のページに埋め込むとき)。

### サーバに配備する (nginx + systemd)

1. `server/` の**中身**を `/opt/yohtube/app/` 直下に (`gamerun.py` が `/opt/yohtube/app/gamerun.py` になるように)、`web/index.html` を `/opt/yohtube/morio/` に置く
2. `deploy/yohtube-game.service` を systemd に登録(gevent 常駐サーバ、**ワーカーは必ず1つ**)
3. `deploy/nginx-morio.conf` で `:8081` に静的ページと `/game/` 中継(WebSocketのUpgrade対応込み)を設定

遅延の演出はサーバ側の `tc`(netem)で行う想定です。例:

```bash
tc qdisc add dev eth0 root netem delay 500ms
```

## テスト

物理・敵・仕掛け・ボス戦・ステージ到達性まで、サーバロジックはヘッドレスで検証できます。

```bash
uv run tests/test_v3.py       server/game.py   # 基本物理とコウラ (25)
uv run tests/test_castle.py   server/game.py   # ボス戦シーケンス (22)
uv run tests/test_features.py server/game.py   # 仕掛け一式 (39)
uv run tests/test_modern.py   server/game.py   # 現代系の補正 (9)
uv run tests/audit_v3.py      server/game.py   # 全ステージの到達性をシミュレーションで監査
```

## 設計メモ (ハマりどころ)

- **gunicorn は WebSocket の Upgrade を 400 で弾く** → gevent の pywsgi を直接使う
- **Flask のルートには `websocket=True` が必須** — Werkzeug は Upgrade ヘッダを見て
  websocket ルールだけを照合するため、無いと WebsocketMismatch で 400 になる
- **simple-websocket の `ping_interval` は使わない** — pingが別グリーンレットから同じソケットに
  書き込み、配信フレームと混線して `Invalid frame header` で切断される。常時配信があるならping不要
- **再接続で `reset` を送らない** — ケーブル抜き差しのたびに進行が消える
- ジャンプは定数でなく **「高さ・上昇秒・落下秒」から逆算** (`_jump_from`) — レベル設計と直結する
- 押下エッジの検出はサブステップ毎ではなく**入力受信時に1回だけ** — さもないと
  1回のバッチ内で再アームされ、1押下で2段ジャンプする
